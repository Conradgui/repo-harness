# ADR-005 · 保留 tool-proxy 薄转发与 memory_pack 功能

**状态**：已执行
**日期**：2026-07-27

---

## 处境

瘦身过程中有两处「看起来该删」但最终决定保留。记录理由，避免后来者重新走一遍。

## 一 · tool-proxy 的 20 个薄转发

`RepoHarness` 里有 20 个这样的方法：

```python
def tool_search(self, args):
    return toolkit.tool_search(self, args)
```

看着是纯样板，占 124 行。删掉能让 god object 小一点。

**决定保留。** 理由：

1. 它们提供 `agent.tool_search(...)` 这个绑定方法 API，工具的实际执行走 `_TOOL_RUNNERS` 是另一条路径，两者并存是有意的
2. `tests/test_safety_invariants.py` 有测试验证转发确实发生——删掉方法就要删掉这个测试
3. 净收益只有 33 行（实际可删的部分），代价是一个验证真实行为的测试

**god object 的问题在 core 那 46 个方法，不在这些薄转发上。** 拿转发开刀是在容易的地方用力。

## 二 · `memory_pack.py`（1,096 行）

初诊时列入删除清单，理由是「与 `memory.py` 职责重叠」。

**决定保留。** 理由：

1. 那个「重叠」判断**从未被验证**——是基于文件名和体量的猜测
2. 深入后确认它是独立的、有测试的（584 行）、有 CLI 入口（`/memory_pack`）的可用功能
3. **删除死代码和删除工作中的功能是两件事**。前者是清理，后者是产品决策

对比同批处理的 `metrics.py`（1,712 行）、`evaluator.py`（651）、`release_evidence.py`（298）——那三个是**零依赖**的，唯一消费者是它们自己的测试。那是真死重，删得干脆。

## 判据

**删除前必须能回答：谁在用它？**

- 答案是「没有人」→ 删（用符号级引用检查确认，不是 grep 到几个就算）
- 答案是「用户能用到」→ 这是产品决策，交给产品负责人，不由执行者顺手做掉

`memory_pack` 的去留仍然开放，判断依据写在 `docs/delivery/04-后续路线图.md`：如果项目定位是「展示完整 agent 能力」就保留，如果是「最小可读的 harness 参考实现」就删。

## 一个反面教材

`tools/` 下有五个模块（`todos.py` / `agents.py` / `ask_user.py` / `plan.py` / `registry.py`）**从未被任何地方 import**。`tools/__init__.py` 自己定义了同名函数把它们全遮蔽了。

`todos.py` 最典型：它的 runner 调回 `agent.tool_todo_*`，而那个又转发到 `tools` 包——落到的是 `__init__` 的实现而不是它旁边那个。**如果真有人 import 了这个模块，这一跳是完全隐形的。**

这类才是该删的：符号级核实确属无引用，删后包能导入、CLI 能启动、13 个工具照常注册、测试不变。
