# ADR-004 · 显式声明 ruff 规则集，而不是锁定版本

**状态**：已执行
**日期**：2026-07-27

---

## 处境

CI 的 lint 步骤长期失败。实测 `origin/main` 上 `ruff check .` 报 **198 个错误**。

根因不是代码差，而是**仓库没有任何 ruff 配置**。`ruff check .` 用的是所装版本恰好携带的默认规则集，而 `pyproject.toml` 写的是 `ruff>=0.4.4`——没有上限，解析到 0.16.0。于是 CI 在为没人选择过的规则失败。

关键观察：核心规则集 `E4,E7,E9,F` 实测 **0 错误**。代码本身是干净的，198 个全部来自 ruff 扩大的默认集。

## 考虑过的选项

**A · 锁定 ruff 版本**
把 `ruff>=0.4.4` 改成一个固定版本，CI 立刻转绿。

**B · 显式声明规则集**
在 `pyproject.toml` 写明选哪些规则族，并给版本一个兼容范围。

## 决策

**选 B。**

A 只是把问题推迟到下次升级。**没有配置的 lint 等于把规则集外包给了版本号**——下一次有人升级 ruff，同样的意外会重演，而且那时没人记得为什么锁的是这个版本。

配置见 `pyproject.toml` 的 `[tool.ruff.lint]`。每个规则族都写了选取理由，`E501`（行长）刻意排除——行长不是这个代码库需要防的东西。

版本仍然给了范围（`>=0.16.0,<0.17.0`），因为新版本可能往已选族里加规则。但这是次要防线，主防线是显式 select。

## 结果

198 → 0。修复过程分三类：

- **54 处自动修复**：导入排序、`getattr(x, "const")` → `x.const`、链式比较
- **7 处显式化**：`subprocess.run` 补 `check=False`。这些调用点都手动检查返回码（rg 无匹配时退出码为 1 是正常情况，`run_shell` 要让 agent 看到失败命令而不是崩溃），所以 `check=False` 是既有语义，只是从未写出来
- **若干处真实改进**：`False if x in y else True` → `x not in y`；`_normalize_tool_args` 的五段近似重复改成声明式表格

## 意外收获

修这 198 个问题时暴露出一个**真实缺陷**：session / task / run 的 id 用 `datetime.now()`（本地时间），而写在同一个 dict 字面量里的 `created_at` 用 UTC。本地时间不单调，DST 回拨会重复一小时，两次相隔一小时的运行可能产生排序颠倒的 id。

详见交付报告 3.4。这条值得记：**lint 不是形式主义，它逼你逐行看过 198 处代码。**
