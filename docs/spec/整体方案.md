# RepoHarness 整体方案

一个 coding agent 的 harness 层：它解决什么问题、为什么这样设计、怎么实现的。

阅读顺序建议：先看第一节（痛点）判断这个项目是否与你相关，再看第三节（架构）理解结构，实现细节在第四节。

---

## 一、要解决的问题

### 1.1 "调模型加个循环"和"能改真实仓库的 agent"之间差什么

让模型输出代码不难。让它**安全地改动一个真实仓库**，中间隔着一层工程——这层就是 harness。

具体到必须回答的问题：

| 问题 | 不处理会怎样 |
|---|---|
| 模型输出格式错了 | 循环卡死或崩溃 |
| 上下文超了 context window | 请求直接失败 |
| 工具输出十万字符 | 一次工具调用吃掉整个上下文 |
| 模型反复调同一个工具 | 无限循环烧 token |
| 模型想写仓库外的路径 | 破坏用户机器 |
| 模型把 `--files` 当搜索词传进来 | 工具行为被模型操纵 |
| 任务失败了，怎么知道它做过什么 | 无法复盘，只能重跑 |

`core/engine.py` 的控制循环本身只有 448 行。上面这些问题的处理构成了其余的代码量——**这就是 harness 这个词的含义**。

### 1.2 三个真实用户痛点

从实际使用中识别的，不是想象的：

**痛点一 · provider 配置是最高频卡点，且失败信号有误导性**

HTTP 404 看起来像服务不可用，实际往往是把只支持 `/chat/completions` 的模型配成了 Responses provider。用户会去查网络、查域名，而问题在配置里。

**痛点二 · agent 行为非确定性，"能复现"是不现实的期望**

同一个任务跑两次路径不同。要求可复现是与模型本质对抗；能**复盘**才是可达成的。

**痛点三 · 安全限制如果表现为"崩溃"，用户会关掉它**

一个动不动就抛异常终止的权限系统，用户的第一反应是加 `--trust-session` 全放开。安全机制必须能让流程继续下去。

## 二、设计取舍

### 2.1 权限决策收敛到单点

所有工具调用经 `PermissionChecker.check()` 求值，工具实现里**不做**能不能做的判断。

代价是这个函数会长。收益是：想知道"什么情况下 agent 能写文件"，读一个函数就够，不用翻十几个工具实现，也不会出现两处判断互相矛盾而无人察觉。

这个取舍被一次真实事故验证过：曾有人在这个函数第一行加了无条件 `deny`，让下方精心实现的 `write_scope` 细粒度校验变成永不可达的死代码。**因为决策集中，这个矛盾一眼可见**；如果散落在各处，它可能永远不会被发现。

### 2.2 拒绝回传模型，而不是抛异常

```python
# 不是 raise PermissionError
return PermissionDecision.deny("write_scope_mismatch", "write_scope_guard")
```

错误码作为下一轮的输入回给模型，模型据此调整策略。用户看到的是 agent 换了个方法，而不是崩溃。

**这让安全约束成为对话的一部分**，而不是打断对话的东西——直接回应痛点三。

### 2.3 为复盘而设计，而不是为复现

每次 `ask()` 产出一组独立工件：

```text
.repo-harness/runs/<run_id>/
├── task_state.json   运行中可观察
├── trace.jsonl       逐步决策流水
└── report.json       结果摘要
```

`run_id` 用 UTC 时间戳 + 随机后缀。用 UTC 是因为本地时间不单调——DST 回拨重复一小时，会让相隔一小时的两次运行产生排序颠倒的 id。

### 2.4 三个诊断命令对应三种不确定

针对痛点一，不是给一个"配置向导"，而是拆成三个命令，各自回答一个不同的问题：

| 命令 | 用户此刻的困惑 |
|---|---|
| `provider probe` | 不知道该选哪个 provider —— 从 endpoint 路径反推 |
| `provider setup` | 知道选什么但不确定怎么写 —— 只存环境变量名，不存 key |
| `provider doctor` | 配好了但跑不通 —— 告诉你配置是否可读、key 是否存在、401/404 各意味着什么 |

`probe` 默认**不发**真实请求，避免用户在探测阶段产生计费。要发必须显式加 `--smoke`。

这是交互设计而非技术设计：把一个"配置失败"的模糊状态，拆成三个用户能自己判断处在哪一步的具体问题。

### 2.5 模型提供的参数是不可信输入

工具参数由模型生成，必须按不可信处理。真实案例：

```python
# 缺 -- 终止符时，模型传 "--files" 会让 rg 去列文件名而不是搜索
["rg", "-n", "--smart-case", "--fixed-strings", "--max-count", "200", "--", pattern, str(path)]
```

`--fixed-strings` 同时防两件事：模型构造的正则触发灾难性回溯（ReDoS），以及与 Python fallback 路径的语义不一致。

**这是 agent 系统特有的攻击面**——传统程序里参数来自开发者，agent 里来自模型。

## 三、架构

### 3.1 分层

```text
入口      cli.py                 参数解析 / REPL / one-shot
             │
装配      build_agent()          workspace · model client · session/run store
             │
运行时    RepoHarness            会话状态 · 工具画像 · checkpoint
             │                   ├─ MemoryCoordinator   记忆审核 / 长期化 / 自迭代
             │                   ├─ WorkerManager       子 agent 编排
             │                   └─ ContextManager      预算与压缩
             │
控制循环  Engine.run_turn        构建 prompt → 调模型 → 解析 → 执行 → 循环
             │
工具执行  ToolExecutor
             ├─ ToolSetProfile   按模式裁剪可见工具
             ├─ PermissionChecker ← 决策点
             └─ tools/           实现
             │
工件      RunStore               task_state / trace / report
```

### 3.2 一次 `ask()` 的时序

1. **装配** —— CLI 参数翻译成运行时对象图
2. **构建 prompt** —— 系统前缀 + 工作区摘要 + 相关记忆 + 当前 profile 可见的工具表。超 context window 时自动压缩历史并重建
3. **调用模型** —— 按 provider 协议路由到 Responses / Chat Completions / Messages
4. **解析输出** —— 识别 `<tool>` 或 `<final>`。格式错误回传纠正提示并重试
5. **权限决策** —— 交给 `PermissionChecker`。拒绝时回传错误码，不中断
6. **执行与记录** —— 结果截断进上下文，完整输出落盘。追加 trace
7. **循环或收敛** —— 回到 2，直到 `<final>` 或 `max_steps`
8. **收尾** —— 写 report，扫描记忆候选进 Review Queue（不直接写长期记忆）

### 3.3 权限决策矩阵

`check()` 按固定顺序求值，先命中先返回。`write_file` 在各场景的实测结果（`python scripts/permission_probe.py`）：

| 场景 | 决策 | reason |
|---|---|---|
| `approval_policy=ask`（默认） | allow | `approval_required` |
| `approval_policy=auto` | allow | `approval_auto` |
| `approval_policy=never` | deny | `approval_denied` |
| `read_only=True` | deny | `read_only_block` |
| `write_scope` 匹配 | allow | `write_scope` |
| `write_scope` 不匹配 | deny | `write_scope_mismatch` |
| plan mode 路径不符 | deny | `plan_mode_path_mismatch` |

### 3.4 记忆的治理形态

长期记忆**不能被 agent 直接写入**：

```text
候选事实 → Review Queue → /memory review accept/edit → 长期 topics
```

理由：agent 判断"什么值得记住"的准确率不足以支撑无人审核的写入。一条错误的长期记忆会污染之后所有会话，而且很难被发现。

`MemoryCoordinator` 承载这条链路。它通过三个回调反向依赖 runtime，而不是持有 runtime 引用——保证依赖方向单一：

```python
persist()               # 写入 session 并落盘
sync()                  # 只写入 session
source_context(origin)  # 记录来源的 session/run/task id
```

## 四、实现要点

### 4.1 双后端语义必须一致

`search` 有两条路径：装了 ripgrep 走 rg，没装走 Python 遍历。两者必须给出相同结果，否则同一个 agent 任务在不同机器上行为不同。

统一为字面匹配契约，smart-case 判断提取为两条路径共用的单一表达式：

```python
case_sensitive = any(character.isupper() for character in pattern)
```

测试通过**断言传给 ripgrep 的 argv** 来验证 rg 路径，而不是要求机器装了 ripgrep——会 skip 的测试等于没测。

### 4.2 子进程编码

```python
subprocess.run(argv, capture_output=True, text=True,
               encoding="utf-8", errors="replace", check=False)
```

缺 `encoding=` 时 Python 用系统 locale 解码。非 UTF-8 主机上读取线程抛 `UnicodeDecodeError`，而**该异常不传播**——它只让 `stdout` 变成 `None`，调用方在很远的地方才报错。这个缺陷曾隔着三层才被定位到。

### 4.3 上下文预算按模型动态计算

不用固定阈值，按 provider 元数据里的 context window 推算：

```python
ctx_window = detect_context_window(model_name, provider_name)
total, sections, floors, recent = compute_budgets(ctx_window, max_new_tokens)
```

超预算时自动压缩历史并重建 prompt，事件记入 event stream（`history_auto_compacted`）。

### 4.4 路径统一收敛

所有路径经 `agent.path()`，越界抛 `path escape`。这是防 agent 写到仓库外的唯一入口，不允许绕过。

## 五、当前状态与边界

### 已具备

- 448 行控制循环 + 工具治理 + 权限决策 + 运行工件
- 5 类 provider 协议：Responses / Chat Completions / Anthropic Messages / DeepSeek / Ollama
- 上下文自动压缩、记忆 Review Queue、子 agent 编排、Skills（兼容 Claude Code 格式）
- 质量门禁：ruff 0 error、测试全绿、全部离线可跑

实时数字：`python scripts/measure.py`

### 已知边界

- `RepoHarness` 仍是 103 方法的大类。`MemoryCoordinator` 已拆出，剩余拆解方案在[路线图](../delivery/04-后续路线图.md) P1
- `run_shell` / `write_file` / `patch_file` 缺专门的契约测试
- `memory.py`（1,265 行）与 `context_manager.py`（644 行）未做深入审计
- sandbox 隔离依赖平台后端，Windows 上能力受限

### 不做的事

- **不做 agent 编排框架**。这是 harness 层，不是 LangGraph 的替代品
- **不做长期记忆的自动写入**。Review Queue 是刻意的摩擦
- **不把 gateway 作为核心依赖**。LiteLLM / OpenRouter 这类当作普通 provider 配置即可

## 六、这个项目验证了什么

**技术上**：harness 层的真实工程量在控制循环之外——格式纠错、上下文治理、输出截断、循环检测、路径收敛、参数注入防护，每一项都是模型不会帮你处理的。

**流程上**：AI 辅助迭代最大的风险不是代码质量，是**方向累积偏移**。这个项目曾有一个 51 commit 的分支，每一轮看起来都在"完成任务"，但 77% 的产出是文档和测试，而 agent 最终连文件都不能改了。识别这件事靠的是量化诊断，不是感觉。
