## 二、决策依据：为什么从 main 重建，而不是修 codex 分支

项目此前在 `codex/repo-harness-phase1-security-kernel` 分支上迭代了 51 个 commit。诊断发现该分支**不可救**，理由是量化的：

### 2.1 分支投入的构成

| 类别 | 新增行数 | 占比 |
|---|---|---|
| 文档 | +6,374 | 41% |
| 测试 | +5,612 | 36% |
| **源码** | **+2,765** | **18%** |

77% 的工作量产出的是文档和测试。而 18% 的源码里，新增的 `repo_harness/security/`（isolation 268 + authorization 123 + staging 55）本身就是封锁机制。

### 2.2 核心能力被四层封锁，且底层实现已删除

| 层 | 位置 | 行为 |
|---|---|---|
| 1 | `tools/__init__.py:553` | `tool_write_file` / `tool_patch_file` 函数体被删，只剩 `raise` |
| 2 | `core/tool_profiles.py:17` | `ToolSetProfile.__post_init__` 从**所有** profile 剥离写工具 |
| 3 | `permissions.py:35` | 权限检查第一行无条件 deny |
| 4 | `auto_issue_fix/runner.py:167` | `_block_on_phase0` |

实测验证（`scripts/permission_probe.py`，两个分支各跑一次，7 种配置 × 2 个写工具 = 14 个场景）：

| 场景 | main | codex 分支 |
|---|---|---|
| 默认 approval=ask | **allow** | deny |
| approval=auto | **allow** | deny |
| plan mode | deny | deny |
| 允许写入的场景数 | **6 / 14** | **0 / 14** |

结论：该分支上的 agent 无法修改任何文件——它不是 code agent，是只读问答系统。而 `main` 的权限分层完好、写入实现完整。

### 2.3 分支测试是红的

`codex` 分支 15 failed / 728 passed。其中 5 个继承自 main，**10 个是该分支自己引入的**，最新 commit `2d62a8c` 就引入了 3 个（`ConfigError: state_root_unavailable`）。

### 2.4 cherry-pick 不可行（实测结论）

对 51 个 commit 做了完整依赖图分析和 dry-run cherry-pick 实测：

- 分支底座 `8eaf1d5` 是一个 **57 文件 / +4,461 行**的 commit，重写了 `tests/conftest.py`。所有后续测试类 commit 都依赖它。
- 保留它 = 一次性吞下 4,461 行测试基建，且它是整条依赖链的根。
- 丢弃它 = 后续 commit 全部无法 cherry-pick，只能手工移植。

因此采用**手工移植**：把真正有价值的修复（rg 参数注入）以补丁形式打到 main 上，而不是 cherry-pick。

## 三、修复的四类真实缺陷

### 3.1 子进程输出编码（影响 37 处调用点）

**症状**：中文 Windows 上测试失败，报 `TypeError: argument of type 'NoneType' is not iterable`。

> **勘误**：本文初版写「5 个测试失败」。在 `origin/main` 的干净 worktree 上复现不出来——实测只有 1 个失败，且是不同的 `FileNotFoundError`。原因是这个缺陷**依赖仓库内容**而非分支：只有当子进程输出含非 ASCII 时才触发，例如工作区里存在中文文件名，`git status --short` 就会输出中文。干净的 `origin/main` worktree 里没有这种内容，所以不触发。
>
> 缺陷本身成立（12 处源码调用点缺 `encoding=` 是可直接核实的事实），但「main 上有 5 个失败」这个论据不成立，不应作为证据使用。

**根因**：所有 `subprocess.run(..., text=True)` 都没有指定 `encoding=`。Python 使用系统 locale 编码（中文 Windows 是 GBK）解码子进程输出，遇到 UTF-8 字节抛 `UnicodeDecodeError`。

**为什么长期未被发现**：解码错误发生在 subprocess 的**读取线程**里。线程崩溃后 `.stdout` 变成 `None`，调用方才在使用时报错。错误信息完全指不到真正的原因。

**影响范围远超测试**：`run_shell`、`search` 的 rg 路径、sandbox runner 都在此列。agent 执行任何输出含非 ASCII 的命令，拿到的都是 `None`。

**修复**：12 处源码 + 25 处测试统一加 `encoding="utf-8", errors="replace"`。`errors="replace"` 保证真正的非 UTF-8 输出（二进制、混合编码）不会再次让读取线程崩溃。

### 3.2 搜索工具双后端语义不一致 + 两个安全缺口

**症状**：同一次搜索，装没装 `ripgrep` 结果不同。

**根因**：
- rg 路径把 pattern 当**正则**
- Python fallback 是 `pattern.lower() in line.lower()`，当**字面量**且总是忽略大小写

**附带的两个安全缺口**：
- 缺 `--` 终止符：以 `-` 开头的 pattern 被 rg 当作选项。模型传入 `--files` 会让工具列文件名而非搜索——模型可以通过 pattern 参数操纵工具行为。
- 缺 `--fixed-strings`：模型提供的 pattern 被编译成正则，可触发灾难性回溯（ReDoS）。

**修复**：统一为字面匹配契约。rg 加 `--fixed-strings` 和 `--`，smart-case 判断（仅当 pattern 含大写时区分大小写）提取为两条路径共用的单一表达式。

### 3.3 零测试覆盖的核心工具

`tool_search` 此前**完全没有测试**。新增 `tests/test_search_tool.py`，13 个用例。

设计要点：rg 后端通过**断言 argv** 来验证，而不是要求机器上装了 ripgrep。这样开发机和 CI 行为一致——**会 skip 的测试等于没测**。

已验证测试是有效的：撤销源码修复后，13 个中有 4 个立即变红。

---

### 3.4 标识符时间戳与 `created_at` 用了两套时钟

**症状**：无报错。这是一个只在跨时区比对或 DST 切换时才会显形的问题。

**根因**：session / task / run 的 id 用 `datetime.now()`（本地时间）生成，而写在**同一个 dict 字面量里**的 `created_at` 用的是 UTC：

```python
"id": datetime.now().strftime("%Y%m%d-%H%M%S") + "-" + uuid.uuid4().hex[:6],  # 本地
"created_at": now(),                                                          # UTC
```

**为什么是缺陷**：

- 本地时间不单调。DST 回拨会重复一小时，两次相隔一小时的运行可能产生**排序颠倒**的 id
- id 与自己的 `created_at` 相差一个本地时区偏移，排障时对不上
- 运行工件跨机器比对时基准不一致

**修复**：四个调用点统一走 `workspace.id_timestamp()`。新增 `tests/test_identifiers.py` 六个用例钉住 UTC 契约，其中一个专门断言 id 与它自己的 `created_at` 一致。

已验证测试有效：把 helper 改回本地时间，6 个中有 5 个立即变红（本机 UTC+8）。

## 四、拆除的反重构机制

### 4.1 最小行数棘轮

`tests/test_architecture_boundaries.py` 整个文件只有一个测试，对 10 个模块强制**最小行数**：

```python
minimum_lines = {"repo_harness/core/tool_executor.py": 120, ...}
assert len(lines) >= minimum, f"{relative} still looks like a shim"
```

**代码变短就失败。** 这是项目只增不减的直接机制——任何精简都要先和测试套件打架。

它本身是上一轮重构翻车的疤：模块被拆到 `core/` 和 `features/`，顶层留下 shim（`worker_manager.py` 5 行、`skills.py` 12 行），有人加了这个测试防止真模块再被掏空。

### 4.2 文档散文断言

`test_repo_harness.py` 中 11 个函数断言特定句子出现在特定 markdown 文件里，包括中文散文：

```python
assert "文档同步是功能完成后的必需门禁" in maintainer_readme
```

这类测试**焊死措辞而不保护正确性**：任何改写都会失败，而链接指向已删除文件时它照样通过。

### 4.3 替换方案

删除 309 行字符串匹配，新增 `tests/test_docs_integrity.py`（37 个参数化检查，随文档数增长），验证真正重要的东西：

- 全部内部 markdown 链接可解析
- README 指向的 getting-started 指南存在
- 指南让读者运行的 CLI 入口在打包配置里已声明
- 没有空的 markdown 文件
