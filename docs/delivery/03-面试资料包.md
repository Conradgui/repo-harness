# RepoHarness 面试资料包

面向：AI 产品经理 / AI 产品架构师岗位
项目定位：从零用 Python 实现的 coding-agent harness，并完成一次完整的技术债治理

## 一、一句话定位（30 秒版）

> 我从零实现了一个本地 coding agent 的 runtime——不只是调模型，而是完整的 harness：控制循环、工具治理、权限决策、运行工件。项目跑偏后，我做了一次系统诊断，把源码降了约 15%，lint 从 198 个错误降到 0，测试从 5 failed 变成全绿，同时修掉了 4 类此前没被发现的真实缺陷。

**为什么这个开场有效**：它同时给出了「做了什么」（构建）和「怎么管的」（治理），而不是只说前者。多数候选人只讲功能，讲不出工程判断。

## 二、2 分钟完整版

**背景**
市面上 coding agent 的产品形态在快速收敛，但我想搞清楚一件事：让一个 agent 能安全地改动真实仓库，工程上到底难在哪。所以我没有用现成框架，而是从零实现了 harness 层。

**做了什么**
核心是一个 448 行的控制循环，加上工具层、权限层、上下文治理和运行工件。支持 5 类 provider 协议（Responses / Chat Completions / Anthropic Messages / DeepSeek / Ollama）。

**遇到的问题**
项目用 AI 辅助迭代了 51 个 commit 之后，我发现越迭代越难改。做了量化诊断，结论很难看：那 51 个 commit 里 77% 的产出是文档和测试，真正的源码只占 18%，而且其中相当一部分是在给系统加限制。最严重的是——agent 已经不能改文件了。

**怎么定位的**
我写了一个权限探针，在两个分支上跑同一组场景。旧分支 0/14 允许，新主干 6/14 允许——探针已提交为 `scripts/permission_probe.py`，任何人都能复算。然后往下追，发现写入能力被四层封锁，最底层的 `tool_write_file` 函数体直接被删了，只剩一句 raise。

**怎么决策的**
我算了一笔账：在旧分支上"解锁"要恢复被删实现、拆四层封锁、修 15 个失败测试、还要拆掉一个"代码不许变短"的测试。这实质上等于把主干已有的代码重写一遍。所以我放弃那个分支，从主干重建，只把真正有价值的两个修复手工移植过来。

**结果**
每个提交独立可回退。测试全绿，ruff 从 198 个错误降到 0，源码降 15.7%。过程中还发现并修复了 4 类此前没暴露的缺陷，其中一个是安全问题。

## 三、四个能力维度的证据

面试官不会因为你说"我懂技术"就相信你。下面每条都配了可验证的证据。

### 3.1 懂技术

**证据 A：能定位隔了三层的间接缺陷**

表层症状是 `TypeError: argument of type 'NoneType' is not iterable`。

追踪链路：
1. `completed.stdout` 为什么是 `None`？`capture_output=True` 正常必返回字符串
2. 完整输出里有条被 pytest 降级成 warning 的信息：`UnicodeDecodeError: 'gbk' codec`
3. `subprocess` 用独立线程读管道，线程内异常不传播——它只是让 buffer 为空
4. `text=True` 让 Python 用系统 locale 解码，中文 Windows 是 GBK，子进程输出是 UTF-8

根因距离报错位置隔了三层，且关键线索被测试框架归类成了 warning。

**证据 B：能识别语义不一致这类"不报错的错"**

`search` 工具有两个后端。rg 路径把 pattern 当正则，Python fallback 当字面量且总是忽略大小写。同一次搜索，装没装 ripgrep 结果不同。这类问题不会报错，只会让 agent 的行为在不同机器上不可复现。

**证据 C：能看出安全缺口**

rg 调用缺 `--` 终止符——模型传入 `--files` 会让工具去列文件名而不是搜索。这意味着**模型可以通过它自己填的参数改变工具行为**。这是 agent 系统特有的攻击面：工具参数由模型生成，就必须当作不可信输入。

### 3.2 懂工程管理

**证据 A：能量化技术债，而不是凭感觉说"代码很乱"**

| 类别 | 51 个 commit 的产出 | 占比 |
|---|---|---|
| 文档 | +6,374 行 | 41% |
| 测试 | +5,612 行 | 36% |
| 源码 | +2,765 行 | 18% |

有了这张表，"要不要放弃这个分支"就从争论变成了算术。

**证据 B：能识别流程本身的病灶**

我把那 51 个 commit 的模式总结出来：

```text
写计划文档 → 实现 → 发现风险 → 删掉实现加 gate → 写文档说明 gate → 加测试断言文档写了 gate
```

每一轮都"完成了任务"，但产出是限制而不是能力。这不是某个人的失误，是**迭代的收尾方式**错了。我据此定了三条规矩：安全边界用开关不删实现；每轮以能跑通的功能收尾；测试只测行为。

**证据 C：能做「不做什么」的决策**

初诊时我把 `memory_pack.py`（1,092 行）列进了删除清单，理由是"与 memory.py 职责重叠"。深入后发现它是独立的、可用的、有测试的功能——我从没验证过那个"重叠"的判断。

于是我改了决定，保留它，并在交付报告里标注为「可选精简项，由产品负责人决定」。**删除死代码和删除工作中的功能是两件事**，后者是产品决策，不该由执行者顺手做掉。

### 3.3 懂质量管理

**证据 A：识别出"反重构棘轮"**

代码库里有一个测试，对 10 个模块强制最小行数：

```python
assert len(lines) >= minimum, f"{relative} still looks like a shim"
```

**代码变短就失败。** 这是项目只增不减的直接机制。任何精简都要先和测试套件打架。

它本身是上一轮重构翻车留下的疤——模块被拆走后顶层留下 shim，有人加了这个测试防止真模块再被掏空。它解决了一个真问题，但用的是会持续收税的方式。

**证据 B：区分"测行为"和"测措辞"**

删掉的 11 个测试断言特定句子出现在特定文档里，包括 `assert "文档同步是功能完成后的必需门禁" in readme`。这类测试改写措辞就失败，而链接指向已删文件时照样通过——它保护的是文本，不是正确性。

替换方案不是简单删除，而是换成真正的完整性检查：全部内部链接可解析、README 指向的指南存在、指南让用户运行的 CLI 入口在打包配置里已声明。309 行字符串匹配换成一组参数化的完整性检查。

**证据 C：验证测试本身是否有效**

新增测试后我做了反向验证——撤销源码修复，看测试是否变红：

```text
撤销修复：4 failed, 9 passed
恢复修复：13 passed
```

**没做这一步的测试是不可信的**，它可能因为断言太松而恒真。

**证据 D：拒绝会 skip 的测试**

第一版 search 测试在没装 ripgrep 的机器上跑出 `1 passed, 5 skipped`——5 个用例什么都没验证。重写成断言传给 ripgrep 的 argv，不再依赖它是否安装。开发机和 CI 行为一致。

### 3.4 懂用户痛点 / 会交互与流程设计

**证据 A：为最高频的卡点设计专门的诊断入口**

provider 配置是新用户最容易卡住的地方，失败信号还特别有误导性——HTTP 404 看起来像服务不可用，实际往往是把只支持 `/chat/completions` 的模型配成了 Responses provider。

所以工具提供三个命令，对应三种不同的不确定：

| 命令 | 解决的问题 |
|---|---|
| `provider probe` | 不知道该选哪个 provider——从 endpoint 路径反推 |
| `provider setup` | 知道选什么但不确定怎么写——只存环境变量名，不存 key |
| `provider doctor` | 配好了但跑不通——告诉你配置是否可读、key 是否存在、401/404 各意味着什么 |

`probe` 默认**不发**真实请求，避免用户在探测阶段产生计费。要发必须显式加 `--smoke`。

**证据 B：把安全约束变成对话的一部分**

权限拒绝不是抛异常终止，而是把错误码回传给模型作为下一轮输入。模型据此调整策略。这让权限系统成为流程的一环，而不是硬中断——用户看到的是 agent 换了个方法，而不是崩溃。

**证据 C：为"事后复盘"设计**

每次 `ask()` 生成一组独立工件：`task_state.json`（运行中可观察）、`trace.jsonl`（逐步决策）、`report.json`（结果摘要）。agent 的行为是非确定性的，**能复盘比能重现更现实**。

**证据 D：从缺失中发现需求**

我给这个项目提的第一个 PR，修的是文档里没写 `/exit` 和 `/quit`。命令一直存在，但一个面向新手的指南从头到尾没告诉读者怎么退出 REPL。这不是大问题，但它是典型的"作者视角盲区"——写文档的人早就知道怎么退出了。

## 四、高频追问与应答

**Q：这不就是调 API 加个循环吗？**

A：循环本身确实不难，448 行。难的是循环之外：模型输出格式错了怎么办（回传纠正提示重试）；上下文超了怎么办（自动压缩历史并重建 prompt）；工具输出太长怎么办（截断进上下文、全文落盘）；模型反复调同一个工具怎么办（检测重复调用并拒绝）；怎么保证它不会写到仓库外面（所有路径经统一收敛函数）。这些都是循环之外的工程量，也是 harness 这个词的含义。

**Q：为什么不用 LangChain / LlamaIndex？**

A：如果目标是交付产品，我会用。这个项目的目标是搞清楚 harness 层到底在处理什么问题——用框架就把这层封装掉了。实际收益是：现在看任何 coding agent 产品，我能判断它的权限模型、上下文策略、工具治理是怎么设计的，也能判断一个 agent 相关的需求实现成本大概在哪。

**Q：AI 写的代码你怎么把关？**

A：这个项目本身就是答案。AI 辅助迭代了 51 个 commit，每一轮看起来都在"完成任务"，但整体在往错误方向累积——最后 agent 连文件都不能改了。

我的结论是：**AI 很擅长完成你交给它的任务，不擅长判断这个任务该不该做。** 所以把关点不在代码审查，在任务定义和收尾验收。具体到规矩就是那三条：安全边界用开关不删实现、每轮以能跑通的功能收尾、测试只测行为不测形状。

**Q：你最大的失误是什么？**

A：诊断阶段我说过"改动集中在 permissions.py 一个文件，风险可控"。错得离谱——实际是四层封锁，最底层的实现已经被删了。只改那一个文件什么用都没有。

问题出在我基于单点发现就下了范围结论。后来用户问我"确定完全梳理清楚了吗"，我重新做了系统排查，才发现四层封锁、测试是红的、还有那个最小行数棘轮。

教训是：**症状的根因可能不止一处，找到一个就停会低估工作量。** 后来我改了做法——下范围结论前先做一次穷举扫描，比如用 AST 遍历找出所有同类调用点，而不是 grep 到几个就算数。

**Q：这个项目还有什么问题没解决？**

A：三个，我都写在交付报告里了：

1. `RepoHarness` 是 god object。记忆子域三步拆解已完成——结果字段收敛成值对象、17 个方法迁入 `MemoryCoordinator`、持久化经三个回调解耦。prompt / checkpoint / metrics 三个聚类可按同样方式迁出，方案在路线图里。
2. `memory.py` 和 `context_manager.py` 没做深入审计。
3. 交付文档里的数字曾经出错两轮——我建了一个 stage-gate 审核 agent 专门复算，它第一次跑就判了 fail、列了 14 项。这件事本身写进了 ADR-006。

我倾向于把已知问题写清楚，而不是在交付时假装它们不存在。
