## 三、关键测试设计决策

### 3.1 会 skip 的测试等于没测

新增 `test_search_tool.py` 时，第一版用「装了 rg 就对比两个后端，没装就 skip」。在开发机上跑出 `1 passed, 5 skipped`——**5 个用例什么也没验证**。

重写方案：

- **Python fallback**：直接执行，真实验证语义
- **rg 后端**：monkeypatch `subprocess.run`，**断言传给 ripgrep 的 argv**

```python
def test_pattern_is_terminated_so_it_cannot_become_an_option(self, ...):
    tool_search(agent, {"pattern": "--files"})
    argv = captured_rg_argv["argv"]
    assert "--" in argv
    assert argv.index("--files") > argv.index("--")
```

结果 `13 passed, 0 skipped`，且开发机与 CI 行为一致。

### 3.2 测试必须能抓住它声称防护的 bug

新增测试后立即做了反向验证——撤销源码修复，看测试是否变红：

```text
撤销修复后：4 failed, 9 passed
恢复修复后：13 passed
```

**没做这一步的测试是不可信的。** 它可能因为断言写得太宽松而恒真。

### 3.3 测行为，不测措辞和形状

移除的两类测试及原因：

| 类型 | 例子 | 问题 |
|---|---|---|
| 最小行数断言 | `assert len(lines) >= 120` | 代码变短就失败，阻止一切精简 |
| 文档散文断言 | `assert "文档同步是必需门禁" in readme` | 改写措辞就失败；链接指向已删文件时照样通过 |

替换为真正的完整性检查：

```python
@pytest.mark.parametrize("doc", [...每个 md 文件...])
def test_internal_links_resolve(doc):
    broken = [link for link, resolved in _internal_targets(doc) if not resolved.exists()]
    assert broken == [], f"{doc} links to missing paths: {broken}"
```

前者检查文件"看起来像什么"，后者检查文档集"是否自洽"。

### 3.4 离线优先

全部 345 个用例**不需要真实 API key**。provider 交互通过两种方式模拟：

- `FakeModelClient`：脚本化模型输出，用于 L1/L2
- 本地 `ThreadingHTTPServer`：真实 HTTP 往返，用于 L3

需要真实 provider 的场景必须显式 opt-in（环境变量），默认跳过。这保证了 CI 无需密钥、无网络依赖、无计费风险。

## 五、缺陷 1 的完整追踪（示例：如何定位间接症状）

这是本次最有价值的一次排查，记录完整链路供复用。

**表层症状**

```text
TypeError: argument of type 'NoneType' is not iterable
  at run_evidence.py:96
      passed = ... and "RepoHarness" in completed.stdout
```

看起来是 `run_evidence.py` 的空值处理问题。

**第一层**：`completed.stdout` 为什么是 `None`？`subprocess.run(capture_output=True)` 正常一定返回字符串。

**第二层**：查看完整输出，发现被 pytest 归类为 warning 而非 error 的信息：

```text
PytestUnhandledThreadExceptionWarning: Exception in thread Thread-1 (_readerthread)
  UnicodeDecodeError: 'gbk' codec can't decode byte 0x80
```

**第三层**：`subprocess` 用独立线程读取管道。线程内的异常不会传播到主线程——它只是让 buffer 保持为空，`stdout` 最终成为 `None`。

**第四层**：为什么用 GBK？`text=True` 让 Python 用 `locale.getpreferredencoding()` 解码。中文 Windows 上是 cp936（GBK）。子进程输出的是 UTF-8。

**根因**：全部 `subprocess.run(text=True)` 调用都没有指定 `encoding=`。

**扫描确认范围**：写脚本遍历 AST，找出所有 `subprocess.run/Popen` 调用，检查是否 `text=True` 且缺 `encoding=`——12 处源码 + 25 处测试。

**教训**：错误信息指向的位置（`run_evidence.py:96`）距离真正的原因（缺 `encoding` 参数）隔了三层。**pytest 把关键线索降级成了 warning**——排查时必须读完整输出，不能只看 `short test summary`。
