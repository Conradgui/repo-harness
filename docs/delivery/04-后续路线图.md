## P1 · 拆解 `RepoHarness` god object

**问题**：`runtime.py` 中单个类有 115 个方法，职责涵盖 plan mode、工具画像、checkpoint、记忆、记忆审核、skills、workers、指标、token 估算、压缩、自迭代。

这是「改一处牵动全身」的直接原因，也是本项目最难改动的地方。

**为什么本次没做**：115 个方法的拆分有多种取舍（按领域拆 / 按生命周期拆 / 提取协作者对象），不同选择影响后续所有扩展。这是架构决策，应该先确认方向再动手，不适合在一次交付里顺手做掉。

### 实测的方法聚类（AST 分析结果）

`RepoHarness` 实际 108 个方法、类体 1,497 行：

| 聚类 | 方法数 | 行数 | 提取难度 |
|---|---|---|---|
| core（装配、循环、会话） | 46 | 696 | 应保留 |
| memory | 17 | 192 | 中，见下 |
| tool-proxy（薄转发） | 20 | 124 | 建议保留，见下 |
| prompt | 8 | 138 | 低 |
| checkpoint | 5 | 124 | 低 |
| metrics/context | 5 | 76 | 低 |
| worker / plan / skills | 7 | 19 | 低 |

### 关于 tool-proxy 的 20 个方法：建议保留

它们是 `def tool_search(self, args): return toolkit.tool_search(self, args)` 这样的一行转发。看起来是纯样板，但它们提供了 `agent.tool_search(...)` 这个绑定方法 API，且有测试验证转发确实发生。

删掉只省 33 行，却要连带删掉一个验证真实行为的测试。**不划算，不建议动。**

### `MemoryCoordinator` 的真实阻碍（本次分析的主要产出）

对 17 个记忆方法做了 self 属性依赖分析，结论是**边界不干净**：

| 状态字段 | 被几个方法触及 | 性质 |
|---|---|---|
| `self.memory` | 12 | 干净的核心，应随协作者迁出 |
| `self.session` / `session_path` / `session_store` | 4 | 持久化耦合 |
| `last_durable_promotions` 等 7 个 `last_*` 字段 | 各 1–2 | **真正的阻碍** |

那 7 个 `last_*` 字段是散落的结果回传通道——记忆操作把结果写进 runtime 属性，CLI 和 display 再去读。提取前必须先决定它们怎么办：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 协作者持有 runtime 反向引用，继续写 `last_*` | 省事，但没有真正解耦，只是把代码挪了个位置 |
| B（推荐） | 记忆操作返回结果对象，不再写 runtime 属性 | 干净，但要同步修改 CLI 与 display 的全部读取点 |

**这是架构决策，不是执行细节**，所以本次交付没有动手。选 B 的话，建议顺序：

1. 先把 7 个 `last_*` 字段收敛成一个 `MemoryOutcome` 数据类（此时仍挂在 runtime 上，测试应保持全绿）
2. 再把 12 个只碰 `self.memory` 的方法迁入 `MemoryCoordinator`
3. 最后处理 4 个持久化方法——给协作者注入一个 `persist` 回调，而不是整个 `session_store`

**执行纪律**：一次一步，每步跑全量测试并单独提交。中途失败时才能二分定位。

前置条件已具备：最小行数棘轮已移除，代码现在可以变短而不触发测试失败。

## 长期：防止再次劣化的三条规矩

这三条来自对 51 个 commit 迭代模式的复盘。那个分支的收尾方式是：

```text
写计划文档 → 实现 → 发现风险 → 删掉实现加 gate → 写文档说明 gate → 加测试断言文档写了 gate
```

每轮都"完成了任务"，但产出是限制而不是能力。

**1 · 安全边界用开关，不删实现。**
最致命的一步是把 `tool_write_file` 的函数体删掉换成 `raise`。正确做法是保留实现、加配置项。删掉的能力找不回来，关掉的能力随时能开。

**2 · 每轮迭代以「能跑通的功能」收尾，不以「新增的文档」收尾。**
如果一轮下来只多了文档和 gate，这轮是负产出。

**3 · 测试只测行为。**
不测行数、不测文档措辞、不测文件存在性。这两类测试是重构的水泥——它们不保护正确性，只增加改动成本。
