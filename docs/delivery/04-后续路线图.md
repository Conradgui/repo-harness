## P0 · 修复 CI 的 lint 步骤

**问题**：`main` 上没有 `uv.lock`。CI 跑 `uv sync` 时按 `pyproject.toml` 的 `ruff>=0.4.4` 解析到最新版（当前 0.16.0），报 199 个错误。

**确认过的事实**：本次交付零新增 lint 错误——改动前 199，改动后 199，用 `git stash` 前后对比实测。

**两个方案**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 在 `pyproject.toml` 锁定 ruff 上限，例如 `ruff>=0.4.4,<0.5`，并提交 `uv.lock` | 30 分钟，CI 立刻转绿 |
| B | 保持不锁，修完 199 个错误 | 半天到一天，但之后每次 ruff 升级都可能再红 |

选 A，然后把 B 作为独立任务排期。**先让 CI 变绿再谈改进**——一个长期红的 CI 等于没有 CI。

## P1 · 拆解 `RepoHarness` god object

**问题**：`runtime.py` 中单个类有 115 个方法，职责涵盖 plan mode、工具画像、checkpoint、记忆、记忆审核、skills、workers、指标、token 估算、压缩、自迭代。

这是「改一处牵动全身」的直接原因，也是本项目最难改动的地方。

**为什么本次没做**：115 个方法的拆分有多种取舍（按领域拆 / 按生命周期拆 / 提取协作者对象），不同选择影响后续所有扩展。这是架构决策，应该先确认方向再动手，不适合在一次交付里顺手做掉。

**建议方案**：提取协作者对象，`RepoHarness` 退化为装配点 + `ask()`。

| 提取目标 | 承接的方法 | 预估 |
|---|---|---|
| `MemoryCoordinator` | `memory_text` / `memory_review_*` / `remember_candidate` / `memory_self_iteration_*` / `memory_organize_text` | ~15 个方法 |
| `WorkerCoordinator` | `spawn_worker` / `render_workers` / `drain_worker_notifications` | ~6 个方法 |
| `PromptBuilder` | `build_prefix` / `refresh_prefix` / `_apply_prefix_state` / `tool_signature` | ~6 个方法 |
| `CheckpointManager` | `checkpoint_state` / `current_checkpoint` / `evaluate_resume_state` / `render_checkpoint_text` | ~5 个方法 |
| `SkillsCoordinator` | `render_skills` / `invoke_skill` | ~2 个方法 |

**执行纪律**：一次提取一个协作者，每次提取后跑全量测试并单独提交。**不要一次性重构** ——中途失败时无法二分定位。

前置条件已具备：最小行数棘轮已移除，现在代码可以变短而不触发测试失败。

## 长期：防止再次劣化的三条规矩

这三条来自对 51 个 commit 迭代模式的复盘。那个分支的收尾方式是：

```text
写计划文档 → 实现 → 发现风险 → 删掉实现加 gate → 写文档说明 gate → 加测试断言文档写了 gate
```

每轮都"完成了任务"，但产出是限制而不是能力。

**1 · 安全边界用开关，不删实现。**
最致命的一步是把 `tool_write_file` 的函数体删掉换成 `raise`。正确做法是保留实现、加配置项。删掉的能力找不回来，关掉的能力随时能开。

**2 · 每轮迭代以「能跑通的功能」收尾，不以「新增的文档」收尾。**
如果一轮下来只多了文档和 gate，这轮是负产出。

**3 · 测试只测行为。**
不测行数、不测文档措辞、不测文件存在性。这两类测试是重构的水泥——它们不保护正确性，只增加改动成本。
