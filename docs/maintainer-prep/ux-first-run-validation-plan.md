# 新手引导文档走查:从零实操(真实 deepseek)

> **定位(诚实声明,双 Agent 审核修正)**:这不是"真人用户体验测试"——执行者是 AI Agent,天然无法真实呈现"真人新手会困惑在哪"。这是**以新手视角进行的文档走查 + 工程可行性验证**:
> - 按 docs/getting-started.md 逐步执行,验证"**照文档能否走通**"(文档即产品,文档的可用性就是产品的第一体验)
> - 记录每一步的"摩擦点"(需要思考/查文档/猜的地方),由独立 Agent 从"新手视角"判定
> - **明确局限**:AI 执行者不会"困惑",故"可理解性"判定是推断,非真人实测。若需真实体验数据,需真人参与。

## 一、角色与场景

**角色**:一个从未用过 repo-harness 的开发者,手上有 DEEPSEEK_API_KEY,想"用 repo-harness 写一个 CSV 转 JSON 的小工具"。

**关键**:严格按 getting-started.md 操作,不查其他资料(这是新手唯一引导),记录每步原始输出。

## 二、执行步骤

| 步 | 引导章节 | 操作 | 摩擦点观察 |
|---|---|---|---|
| 1 | 1.安装自检 | `uv sync` + `python -m repo_harness --help` | 输出新手能懂吗? |
| 2 | 2.配置 provider | 按 2.4 DeepSeek:设 `$env:DEEPSEEK_API_KEY`,probe/setup/doctor | **key 放哪?** base_url 反直觉(anthropic client)?照抄能否通? |
| 3 | 启动 | `--repl` | 进去知道怎么问吗? |
| 4 | 真实任务 | 在 REPL/一次性任务中"写一个 csv2json.py" | agent 是否理解?工具调用顺畅? |
| 5 | 验证 | 生成的工具能否运行 | 产出是否可用 |

## 三、DoD(分为两类,分开计数,不混称)

### 体验 DoD(用户视角,可操作化)
| # | 标准 | 可操作判定 |
|---|---|---|
| X1 | 新手能按文档完成安装到配置 | 每步只需看本文档;无需查其他资料 |
| X2 | provider 配置可理解 | key 放置、api_key_env 关系在文档中有明确指示,新手不用猜 |
| X3 | 错误提示可行动 | 若出错,提示含"你应该做 X"(动作),非裸 traceback |
| X4 | 文档"照抄即通" | DeepSeek 示例(base_url/model/api_key_env)零修改能跑通;若需修改,文档缺陷 |

### 工程 DoD(系统正确性,单列)
| # | 标准 | 判定 |
|---|---|---|
| E1 | 真实任务被理解并执行 | agent 生成 csv2json,工具可运行 |
| E2 | 交互无死循环/卡死 | 无无限循环/重复 |
| E3 | 产出有用 | 工具正确处理样例输入 |

**判定**:X1-X4 全满足 = 文档走查通过;E1-E3 全满足 = 工程可行性通过。**两者分开声明,不合并成"体验通过"。** 任一 X 不满足 = 记录为文档/产品缺陷(严重度),并说明。

## 四、摩擦点记录(新手视角)

对每一步,记录:
- 新手是否需要"猜"(文档没写但用户必须知道)?
- 新手是否需要"查文档外资料"?
- 输出是否技术黑话(如 approval/sandbox/tool profile 对新手)?
- 若中途出错,提示是否告诉下一步?

## 五、红线

- 真实 deepseek 调用,任务小,成本可控
- 不触碰第三方仓库、不 push、不修改 repo_harness 源码
- **不表演**:诚实记录摩擦点,不因"能跑"就判体验通过;明确标注 AI 执行者局限
- 体验缺陷被记录后,评估其是否值得单独修复(由用户决策,非自动)

## 六、执行

主 Agent 用 Terminal 按文档逐步执行,收集每步原始输出;随后发起独立走查评估 Agent,从"新手视角"判定 X1-X4 和 E1-E3,并列出摩擦点清单。
